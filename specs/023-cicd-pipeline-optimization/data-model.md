# Phase 1 Data Model: CI/CD Pipeline Optimization

This feature has no application data store — its "entities" are pipeline/version-control constructs, persisted in git, GitHub, and GitHub Actions run storage rather than a database. This document maps the spec's Key Entities to where and how each actually lives.

## Component

**Represents**: An independently versioned, tested, built, and deployed part of the system.

**Instances**: exactly two — `frontend` (`src/frontend/**`), `backend` (`src/backend/**` + `src/function_app.py` + `src/requirements.txt`).

**Attributes**:
- `name` — `frontend` | `backend`
- `path_scope` — the glob(s) that trigger this component's workflow and scope its version history (matches existing `on.push.paths` in each `*-deploy.yml`)
- `current_version` — derived, not stored: the highest semver tag matching this component's `tagFormat` (e.g. `backend-v*`)
- `tag_format` — `backend-v${version}` / `frontend-v${version}`

**Relationships**: A Component has many Releases (one per version bump) and, per workflow run, produces at most one Build Artifact.

**Not modeled as data**: Infrastructure is explicitly not a Component for versioning purposes (FR-014) — it has no `tag_format` and produces no Release.

## Release

**Represents**: A named, versioned point in a Component's history.

**Persisted as**: a git tag (`{component}-v{X.Y.Z}`) + a GitHub Release with that tag, created by `@semantic-release/github` in the `release` job.

**Attributes**:
- `component` — which Component this release belongs to
- `version` — SemVer `X.Y.Z`
- `commit_sha` — the `main` commit (a squash-merge commit, per Clarifications) this release was cut from
- `release_notes` — generated by `@semantic-release/release-notes-generator` from the PR title(s) since the last release
- `created_at` — release timestamp

**Lifecycle**: Created once per qualifying `release` job run (a run with at least one commit since the last tag whose type maps to a version bump — `feat`/`fix`/`BREAKING CHANGE` per Conventional Commits). A run with no qualifying commits since the last release (edge case: only `chore`/`docs`, or commits outside this component's paths) produces no new Release — this is `semantic-release`'s default no-op behavior when the commit-analyzer finds nothing releasable.

**Validation rules** (from FR-007, FR-008, FR-013):
- A Release's version MUST only increment based on commits whose **diff actually touched this Component's paths** — not based on the scope word declared in the commit's PR title, which is descriptive only. A vertical-slice commit touching multiple components' paths is eligible to bump each of them independently (see spec.md User Story 3, Acceptance Scenario 5).
- A Release's version bump type (patch/minor/major) MUST match the highest-impact qualifying commit type since the last Release for this Component (fix→patch, feat→minor, breaking change→major).

## Build Artifact

**Represents**: The single deployable output produced once per pipeline run for a Component.

**Persisted as**: a GitHub Actions run artifact (`actions/upload-artifact`), scoped to that specific workflow run — not a durable, cross-run store (consistent with the spec's out-of-scope: no rollback/redeploy of an older artifact).

**Attributes**:
- `component` — which Component this artifact was built for
- `version` — the Release version stamped into it (or the not-yet-released next-candidate version, if no qualifying commit triggered a new Release this run — see Edge Cases)
- `contents` — backend: a zip of the `src` deploy root (`function_app.py` + `backend/` package + `requirements.txt`); frontend: the built `dist/` directory
- `version_metadata_file` — `VERSION` (backend) / `version.json` (frontend) — see research.md decision #7

**Relationships**: Produced by exactly one `build` job run, consumed by exactly one corresponding `deploy` job run in the same workflow run (FR-001/FR-002). Never reused across workflow runs.

**Validation rule** (FR-001, FR-002, SC-002): The artifact the `deploy` job deploys MUST be byte-identical to the artifact the `build` job produced in the same run — no rebuild step may run between `build` and `deploy`.

## Infrastructure Plan

**Represents**: The reviewed, gated description of infrastructure changes produced during `terraform-apply.yml`'s `validate` job.

**Persisted as**: a Terraform binary plan file (`tfplan`), uploaded as a GitHub Actions run artifact by `validate`, downloaded by `apply` — same run only, matching the plan's own state-dependent validity window.

**Attributes**:
- `plan_file` — the Terraform-generated binary plan
- `source_commit_sha` — the commit the plan was generated against
- `generated_at` — when `validate` ran `terraform plan -out=tfplan`

**Relationships**: Produced by exactly one `validate` job run, consumed by exactly one `apply` job run in the same workflow run, gated by the intervening `test` job and the `production-infra` environment's manual approval.

**Validation rule** (FR-015, FR-016): `apply` MUST invoke `terraform apply` against this exact plan file. If Terraform reports the plan is stale relative to current state, `apply` MUST fail (Terraform's native behavior) rather than falling back to generating a new plan.

**Explicitly not versioned**: An Infrastructure Plan has no `tag_format`, produces no Release, and is not a Component — infra versioning is out of scope (FR-014).
