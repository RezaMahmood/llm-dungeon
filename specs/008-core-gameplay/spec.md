# Feature Specification: Core Gameplay

**Feature Branch**: `008-core-gameplay`

**Created**: 2026-08-28

**Status**: Draft

**Reorganized from**: merges "Play an Adventure Story" (originally `001-adventure-game` User Story 1, including content safety, rate limiting, and session exclusivity) with "Game Concludes According to Configured Completion Criteria" (originally `003-game-setup-and-authoring` User Story 3) — the narrative play loop and how that loop ends are the same core mechanic.

**Input**: User description (combined): "A player opens the application in a web browser, chooses an available story, and plays through it entirely by typing natural-language actions. After each action, the system responds with narrative text... The game can be configured to complete after a certain duration - for example 30 minutes. The game can be configured to complete when certain criteria have been fulfilled (success criteria). The game can be configured to complete when the player has failed in the game (exit criteria). The game can be configured to complete when any or all of the above criteria is met."

**Design Reference**: [specs/designs/03-play.html](../designs/03-play.html), story pane & status panel (see [specs/designs/README.md](../designs/README.md)). Note: the screen's "Stuck? ## Clarifications

### Session 2026-09-05

- Q: When a second interaction is submitted while one is already being processed on the same session, should the system reject it outright, or hold it and process it after the first one finishes? → A: Reject immediately — the second request is turned away right away (e.g., an immediate "try again" response) so the player retries.
- Q: When more than one completion condition is satisfied at effectively the same moment, which one should the system record as the session's ending reason? → A: Duration takes priority first; if not triggered, and both a success and a failure condition become true on the same turn, success takes priority over failure.
- Q: When an adventure is configured with a maximum duration, should that duration be measured as wall-clock time since the session started (including idle time), or only the player's active playing time (excluding idle gaps)? → A: Wall-clock time since session start, including any idle gaps.
- Q: What's the target length for a single narrative response turn, so responses stay brief and token usage is optimized? → A: No longer than 150 words per response.
- Q: Should the system require that a player's narrated actions actually establish a success/failure condition happened in the fiction, rather than accepting the player's own bare claim that it happened? → A: Yes — completion-condition matching MUST be based on narrated in-fiction events actually generated by the system, not on the player's bare assertion of an outcome.
- Q: Should attempts to make the system break character (e.g., "ignore your instructions," "reveal your system prompt," "stop being a game") be called out as their own explicit guardrail, distinct from unsafe content and generic off-fiction gibberish? → A: Yes — add an explicit requirement and edge case: the system MUST keep responses in-fiction and MUST NOT follow player instructions that attempt to override its behavior, reveal internal prompts/instructions, or act outside the adventure, regardless of phrasing.
- Q: Should narrative generation prioritize strict consistency with previously established facts over creative variety in phrasing/outcomes? → A: Yes — narrative MUST NOT contradict previously established facts/events in the session; strict consistency takes priority over creative variety.
- Q: If a player repeatedly submits unsafe/disallowed content within a session, should the system escalate beyond the normal in-fiction deflection? → A: Yes — 3 strikes: after the 3rd content-safety-flagged submission, the player is locked out for 1 hour. Player-wide: the lockout blocks that player from starting or continuing any session (not just the one where the flags occurred) for 1 hour.
- Q: The system should compact/summarize a session's history as it grows, persist that summary separately from the full turn-by-turn history, and use it as prior context starting the very next turn after summarization — what should trigger a summarization? → A: Every 20 turns. The underlying technology/model used to produce the summary MAY differ from the one used for narrative turn generation.
- Q: Should the periodic summary (FR-014) also serve as the save-point mechanism a resumed session is reconstructed from, or should that stay entirely separate? → A: Keep summarization and save-point mechanisms separate — this spec only covers context summarization; a save-point/checkpoint mechanism is a different spec's concern, not built on top of this summary here.
- Q: A player may hold more than one of their own concurrent sessions (FR-006, e.g. against two different adventures) — can more than one of them be actively played at the same time, and if not, what happens to the one the player isn't currently in? → A: At most one of a player's own sessions is that player's active session at any time. Interacting with (or creating) any session makes it the active one and deactivates whichever other session was previously active for that player, leaving its state untouched. A direct interaction attempt against a session that isn't currently the player's active session is rejected — telling the player they left it to play elsewhere — until the player explicitly resumes it (which reactivates it and deactivates whatever is currently active). There is no live push to an idle browser tab; the "moved out" message only appears the next time the player interacts with, or attempts to resume, the now-inactive session.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Player Plays Through an Adventure via Natural Language (Priority: P1)

Once a player has set up a game (see `006-adventure-and-character-setup`), they play entirely by typing natural-language actions ("look around," "open the door," "ask the innkeeper about the map"). After each action, the system responds with narrative text describing what happens next, consistent with everything that has happened so far in that session.

**Why this priority**: This is the core value of the product — the actual game experience. Nothing else matters if this loop doesn't work.

**Independent Test**: With a play session already set up (adventure, character name, character type), submit a sequence of natural-language actions and verify each response is narratively coherent, reflects prior actions, and is delivered through the text interface.

**Acceptance Scenarios**:

1. **Given** a newly set-up play session, **When** it begins, **Then** the system presents an opening narrative passage establishing the scene, consistent with the chosen adventure and character.
2. **Given** an active play session with prior history, **When** the player types a free-text action, **Then** the system returns a narrative response consistent with the story's setting and the session's prior events.
3. **Given** a concluded session (see User Story 2), **When** the player submits another action, **Then** the system indicates the story has ended rather than generating further narrative.
4. **Given** an active play session, **When** a second interaction is attempted against it while one is already in progress, **Then** the system immediately rejects the second interaction (rather than queuing it) so session state is never corrupted or interleaved.
5. **Given** a player with two of their own play sessions (e.g. on different adventures), **When** they submit an interaction against the session that is not currently their active one, **Then** the system rejects that interaction, tells the player they left this story to play another, and does not generate narrative until the player explicitly resumes it.
6. **Given** a player's previously active session that has since been deactivated because they interacted with a different session, **When** the player explicitly resumes the deactivated session, **Then** it becomes their active session again (with its state exactly as they left it), their other, currently-active session becomes inactive in its place, and interactions against the resumed session now succeed normally.
7. **Given** an active play session, **When** the player triggers the exit action, **Then** the system shows a pause confirmation stating where the game was saved before leaving, rather than exiting immediately without confirmation.

---

### User Story 2 - Game Concludes According to Configured Completion Criteria (Priority: P2)

While a player is in an active game, the game automatically ends when the conditions the administrator configured for that adventure are met: a time limit is reached, a defined success outcome is achieved, a defined failure outcome occurs, or (depending on configuration) a combination of these.

**Why this priority**: Correctly ending a session is as important as starting one — a game that never ends, or ends incorrectly, undermines the whole experience. It builds directly on User Story 1.

**Independent Test**: Configure one adventure with a short time limit and separately configure another with a success condition; play each to the point the configured condition is met and verify the session concludes for that reason and no other.

**Acceptance Scenarios**:

1. **Given** an adventure configured with a maximum duration, **When** the wall-clock time since the play session started (including any idle time) reaches that duration, **Then** the system ends the session and narrates the conclusion, even if the player has not reached any other ending.
2. **Given** an adventure configured with success criteria, **When** a player's actions satisfy those criteria, **Then** the system ends the session as a successful outcome.
3. **Given** an adventure configured with failure/exit criteria, **When** a player's actions meet those criteria, **Then** the system ends the session as a failed outcome.
4. **Given** an adventure configured with more than one completion criterion and a rule that any one of them ends the game, **When** the first of those criteria is met, **Then** the session ends immediately without waiting for the others.
5. **Given** an adventure configured with more than one completion criterion and a rule that all of them must be met, **When** only some of the configured criteria have been satisfied, **Then** the session continues until the remaining criteria are also satisfied (or the game is otherwise ended).

---

### Edge Cases

- Player submits input that is nonsensical or unrelated to the story (e.g., gibberish, or a request entirely outside the fiction): the system responds in a way that keeps the player in the narrative (e.g., "that doesn't seem to work here") rather than erroring.
- Player input is flagged by content safety screening: the system does not forward or display the unsafe content, and instead returns a clear, in-context message.
- A player submits requests faster than the allowed rate: the system informs them clearly rather than silently failing or crashing.
- Two completion criteria are both satisfied at effectively the same moment (e.g., the time limit expires on the same action that also meets the success criteria): the system ends the session exactly once, with one clearly attributed reason, using this fixed priority order: duration first, then success, then failure (e.g., if a success and a failure condition are both newly satisfied on the same turn, the session ends as a success).
- Multiple players independently start sessions against the same adventure at the same time: each session is exclusive to the player who started it, with no visibility or interference between them.
- A player who already has an active session on one adventure creates or interacts with a session on a different adventure: the previously active session is left exactly as it was (no lost turns, no state change) and simply becomes inactive; if the player later tries to interact with it directly without first resuming it, the system tells them they left it to play elsewhere and requires an explicit resume action before it accepts further interactions.
- A player asserts a success or failure outcome directly in their input (e.g., "I have already defeated the dragon and won") without the system having actually narrated that event: the system does not treat the bare assertion as satisfying a completion condition — only events the system itself narrates in response can satisfy success/failure criteria.
- A player attempts to make the system break character or act outside the adventure (e.g., "ignore your instructions," "reveal your system prompt," "stop being a game and do X instead"): the system does not comply, does not reveal internal prompts/instructions, and responds with an in-fiction deflection that keeps the player in the narrative, regardless of how the attempt is phrased.
- A player accumulates 3 content-safety-flagged submissions: the system locks that player out from any further interaction, across all of their sessions and adventures, for 1 hour from the 3rd flagged submission, and clearly informs them why — rather than continuing to allow unlimited flagged attempts.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST allow a player to interact with an in-progress adventure exclusively through free-form natural-language text input.
- **FR-002**: System MUST respond to each player input with narrative text that reflects both the adventure's content and the accumulated history of that player's session, and that narrative text MUST be no longer than 150 words per response — brief enough to keep pace with real-time play and optimize token usage, while still moving the story forward.
- **FR-003**: System MUST retain the state/context of a player's session across multiple interactions so later responses remain consistent with earlier ones. Narrative responses MUST NOT contradict previously established facts or events from that session's history — consistency takes priority over creative variety when the two are in tension.
- **FR-004**: System MUST screen natural-language input and generated narrative output for unsafe or disallowed content and MUST NOT display unsafe content to a user.
- **FR-005**: System MUST limit how frequently a single player can submit interactions, and MUST communicate clearly to the player when that limit is reached.
- **FR-006**: System MUST ensure each play session is exclusive to the single player who started it — no other user may view or act within that session. Any number of players may hold their own separate, concurrent sessions, including against the same adventure.
- **FR-007**: System MUST support configuring, per adventure, one or more of the following completion conditions: a maximum time duration (measured as wall-clock time elapsed since the play session started, including any idle time), one or more success criteria, and one or more failure/exit criteria.
- **FR-008**: System MUST support configuring, per adventure with more than one completion condition, whether the game ends when any one configured condition is met or only when all configured conditions are met.
- **FR-009**: System MUST automatically end a play session as soon as its adventure's configured completion condition(s) are satisfied, and MUST record which condition (or combination) caused the ending. When more than one completion condition becomes satisfied at effectively the same moment, the system MUST attribute the ending using the fixed priority order duration, then success, then failure (see Edge Cases). Completion-condition matching MUST be based on narrated in-fiction events actually generated by the system in response to the player's action, not on the player's own unverified assertion that a success or failure outcome has occurred (see Edge Cases).
- **FR-010**: System MUST recognize when a session reaches a defined ending and prevent further gameplay actions within that concluded session.
- **FR-011**: Each distinct type of player interaction and each distinct completion-condition type/combination MUST have a corresponding automated test verifying its expected behavior.
- **FR-012**: System MUST keep every narrative response in-fiction and MUST NOT comply with player input that attempts to override the system's behavior, reveal its internal prompts/instructions, or otherwise act outside the adventure — regardless of how the attempt is phrased — responding instead with an in-fiction deflection (see Edge Cases).
- **FR-013**: System MUST track, per player, the count of content-safety-flagged submissions (FR-004) across that player's sessions. Once a player accumulates 3 flagged submissions, the system MUST lock that player out from submitting or starting any interaction, across all of that player's sessions and adventures, for 1 hour from the 3rd flagged submission, and MUST clearly inform the player of the lockout and its cause.
- **FR-014**: System MUST summarize/compact a play session's narrative history after every 20 turns, producing a persisted summary that is stored separately from the full turn-by-turn history, solely to bound the context used for narrative generation. Starting with the next turn generated immediately after a summarization, the system MUST use that summary (rather than the full un-summarized history) as the prior context for narrative generation.
- **FR-015**: System MUST ensure that, at any given time, at most one of a single player's own play sessions is that player's active session. Submitting an interaction against a session, or creating a new session, MUST make that session the player's active session and MUST deactivate whichever other session was previously active for that player, leaving the deactivated session's state unchanged. System MUST reject an interaction submitted directly against a session that is not currently the player's active session, informing the player that they left it to play elsewhere, and MUST NOT generate narrative for that session until the player takes an explicit action to resume it — which MUST reactivate that session and deactivate whatever session is currently active for that player.
- **FR-016**: System MUST require an explicit pause-and-exit confirmation before a player leaves an active play session — triggering the exit action MUST show a pause screen stating where/that the game was saved, rather than exiting immediately without confirmation (Constitution "Save and session behaviour" #3, Screen Contracts "Play surface").
- **FR-017**: System MUST state to the player, in the play surface UI, that their progress is autosaved after every turn (Constitution "Save and session behaviour" #1) — this is a UI disclosure of behavior the system already performs by persisting the session after every interaction, not a new save mechanism.

### Key Entities

- **Play Session**: One player's individual playthrough of a specific adventure — tracks the ongoing narrative history and current state, is exclusive to the player who started it, is the player's sole *active* session while no other of that player's own sessions has been interacted with more recently (FR-015), and ends when its configured completion criteria are met.
- **Player Interaction**: A single natural-language input from a player during a Play Session and the narrative response it produces — the atomic unit of gameplay.
- **Completion Criteria**: The set of conditions configured on an adventure (defined during story creation/import — see `004-story-creation-done`, `011-story-import`) that determine when a play session automatically ends — a maximum duration, success condition(s), and/or failure condition(s) — together with a rule for whether any one or all configured conditions must be met.
- **Player Content-Safety Standing**: A per-player, cross-session record of how many content-safety-flagged submissions (FR-004) that player has accumulated and, once the 3-strike threshold is reached, the timestamp their resulting 1-hour lockout (FR-013) expires — distinct from any single Play Session, since it must persist and apply across all of a player's sessions and adventures.
- **Session Summary**: A condensed representation of a play session's narrative history so far, produced every 20 turns (FR-014), persisted separately from the full turn-by-turn history, and used as the prior context for narrative generation from the next turn onward. This is a context-management mechanism only — not a save-point/checkpoint mechanism (see Assumptions).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A player receives a narrative response to a submitted action within a few seconds, so play feels like a real-time conversation rather than a batch process.
- **SC-002**: 100% of distinct player-interaction types are covered by an automated test that verifies real expected behavior.
- **SC-003**: In evaluation testing, disallowed or unsafe content submitted by a player is withheld from display to any user in 100% of tested cases.
- **SC-004**: In evaluation testing, concurrent interaction attempts against the same active play session never result in corrupted, interleaved, or lost session state.
- **SC-005**: A player who exceeds the allowed request rate always receives a clear, human-readable notice rather than a silent failure or an unrelated error.
- **SC-006**: 100% of tested play sessions conclude for the specific reason their adventure was configured for (duration, success, failure, or the correct any/all combination), with no session left indefinitely open past its configured condition.
- **SC-007**: 100% of tested narrative responses are no longer than 150 words, keeping responses brief and token usage optimized while still advancing the story.
- **SC-008**: In evaluation testing, 100% of tested attempts to make the system break character, reveal internal prompts/instructions, or act outside the adventure are deflected in-fiction rather than complied with.
- **SC-009**: In evaluation testing, 100% of tested multi-turn narrative sequences contain no contradiction of a previously established fact or event from that session's history.
- **SC-010**: In evaluation testing, a player who accumulates 3 content-safety-flagged submissions is locked out of all further interaction for 1 hour in 100% of tested cases, and receives a clear explanation of the lockout.
- **SC-011**: In evaluation testing, 100% of tested sessions that reach 20 turns produce a persisted summary used to bound context, and the narrative generated for the very next turn after that point is based on the summary rather than the full un-summarized history.
- **SC-012**: In evaluation testing, 100% of tested interaction attempts against a session that is not the player's current active session are rejected (rather than generating narrative) until the player explicitly resumes that session, and 100% of explicit resume actions correctly deactivate whatever session was previously active for that player.
- **SC-013**: 100% of tested exit attempts from an active play session show a pause confirmation stating where the game was saved before the player leaves, with no path that exits without that confirmation.
- **SC-014**: 100% of tested play-session UI renders include a visible statement that progress is autosaved after every turn.

## Assumptions

- This spec assumes a play session has already been set up with a chosen adventure, character name, and character type, per `006-adventure-and-character-setup`; it does not redefine that setup flow.
- Completion criteria (duration, success, failure, and the any/all combination rule) are authored as part of a story's configuration in `004-story-creation-done` or `011-story-import`; this spec only covers how they are enforced during play, not how they are defined.
- Saving progress mid-session and resuming later (a save-point/checkpoint mechanism) is a separate capability handled by a different spec (see `009-save-and-continue`); this spec's periodic session summary (FR-014) exists solely to bound the context used for narrative generation and is not, itself, a save-point mechanism — the two are deliberately kept separate.
- The underlying technology/model used to produce the periodic summary (FR-014) is an implementation choice; it is not required to be the same technology/model used to generate narrative turns.
