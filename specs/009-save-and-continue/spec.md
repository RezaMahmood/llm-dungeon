# Feature Specification: Save and Continue

**Feature Branch**: `009-save-and-continue`

**Created**: 2026-08-28

**Status**: Draft

**Reorganized from**: merges "Player Continues a Saved Game" and "Player Saves Progress and Returns Home" — originally User Stories 2 and 4 within `003-game-setup-and-authoring` — into a single persistence-focused domain, split out from core gameplay (`008-core-gameplay`) since saving/resuming across visits is a distinct concern from the moment-to-moment play loop.

**Input**: User description (combined): "Continue Game: Select games associated to profile; Play Game; End/Save Game; Return to Home Page. Save Game: Game state is saved; Return to Home page. Logout: Ask player to save game (if they are currently in a game)."

**Design Reference**: [specs/designs/02-story-select.html](../designs/02-story-select.html), "stories in progress" / Resume section, and [specs/designs/03-play.html](../designs/03-play.html), checkpoint-save/pause-and-exit controls (see [specs/designs/README.md](../designs/README.md))

## Clarifications

### Session 2026-09-06

- Q: When a player explicitly saves during a game, does that create a named checkpoint they can later go back to, or is it simply a confirmation that their already-autosaved progress is safe? → A: Named checkpoint marker — an explicit save records a labelled, timestamped marker on the session and confirms visibly, but resuming always continues from the latest state; markers are history/labels, not rewind points.
- Q: What should actually differ between accepting and declining the "save before you log out?" prompt, given autosave already persists every turn? → A: Accepting records a checkpoint marker and confirms the game is saved; declining records no marker. Progress is identical either way, and the prompt tells the player their progress is already safe.
- Q: Where does a checkpoint marker's label come from — is it generated by the system, or does the player type it? → A: System-generated only — derived from the game's current in-fiction location and the save time; the player never types a name.
- Q: When a player picks a game from the continue list while a different game of theirs is still their current one, should the switch just happen, or should the system confirm first? → A: Switch silently — resuming any unconcluded game makes it the player's active game and sets aside whichever was active before (state untouched); the continue list visibly marks which game is the active one.
- Q: If recording the checkpoint fails (backend or network error) when the player saves or accepts the logout prompt, what should the system do? → A: Proceed anyway — tell the player the checkpoint could not be recorded but their progress is safe, then complete the logout or return home as requested.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Player Continues a Saved Game (Priority: P1)

A returning player chooses "continue game," sees the games associated with their own profile, and resumes one from where they left off.

**Why this priority**: Long-form play across multiple visits depends on this; it is the primary reason persistence exists at all.

**Independent Test**: With a player who has one previously saved, in-progress game, select "continue game," verify only that player's own saved games are listed, and verify resuming one restores the prior narrative state.

**Acceptance Scenarios**:

1. **Given** a player has one or more saved, in-progress games, **When** they choose "continue game," **Then** they see a list of only their own saved games, not any other player's.
2. **Given** a player selects one of their saved games, **When** the game resumes, **Then** play continues from the saved state, consistent with everything that happened before it was saved.
3. **Given** a player has no saved, in-progress games, **When** they choose "continue game," **Then** they see a clear indication that there is nothing to continue, rather than an empty or broken screen.
4. **Given** a player has a different game of their own as their currently active game, **When** they resume another game from the continue list, **Then** the chosen game becomes their active game without asking them to confirm, the previously active game is set aside with its state unchanged, and the list shows which game is the active one.

---

### User Story 2 - Player Saves Progress and Returns Home (Priority: P2)

At any point during an active game, a player can explicitly save their current progress and return to the stories screen — the screen listing their in-progress games and the adventures they can start — and the system also offers to save when the player tries to log out while a game is in progress.

**Why this priority**: This gives players a deliberate, reassuring way to step away mid-game and confirms their progress is safe before they leave; it's a safety-net capability layered on top of an already-working play loop and login flow.

**Independent Test**: Start a game, take a few actions, explicitly save and leave to the stories screen, then verify — by reading that game's stored state directly, without relying on User Story 1's continue screen — that it retains every turn taken and carries a checkpoint marker for the save. Separately, sign out once accepting the save prompt and once declining it, and verify the retained turns are identical both times.

**Acceptance Scenarios**:

1. **Given** a player is in an active, unconcluded game, **When** they choose to save and leave, **Then** the current game state is persisted and the player is returned to the stories screen.
2. **Given** a player is in an active, unconcluded game, **When** they attempt to log out, **Then** the system asks whether they want to save their progress before logging out, telling them their progress is already safe either way.
3. **Given** a player is prompted to save on logout and chooses to save, **When** they next log in and continue that game, **Then** their progress from just before logout is present and a checkpoint marker records that save.
4. **Given** a player is prompted to save on logout and declines, **When** they next log in and continue that game, **Then** their progress from just before logout is equally present, with no checkpoint marker recorded for the declined save.
5. **Given** a player is not currently in an active game, **When** they log out, **Then** they are not prompted to save.

---

### Edge Cases

- Recording the checkpoint marker fails (backend or network error) during an explicit save or an accepted logout save: the player is told the checkpoint could not be recorded but their progress is safe, and the logout or return-home they asked for still completes — a failed marker never blocks the player from leaving.
- A player's game already ended (via a completion criterion — see `008-core-gameplay`) before they log out: they are not prompted to save, since a concluded game has nothing further to save.
- A player explicitly saves the same game twice in a row without taking any action in between: the second save succeeds and leaves the game state unchanged, recording a second checkpoint marker at the same point in the narrative.
- A player has multiple saved, in-progress games across different adventures: the continue-game list distinguishes them clearly enough for the player to pick the right one, and marks which one is currently active.
- A player resumes the game that is already their current, active game: the resume succeeds and simply returns them to it, with no other game set aside and no error shown.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST allow a player to view and resume any of their own previously saved, in-progress games, and MUST NOT show a player another player's saved games. The list MUST visibly identify which of those games, if any, is currently the player's active game (see `008-core-gameplay` FR-015).
- **FR-001a**: Resuming a game from the continue list MUST make it the player's active game and set aside whichever game was active before — leaving that game's state unchanged — without asking the player to confirm the switch, and MUST leave the resumed game immediately playable rather than in a state that rejects further input.
- **FR-002**: System MUST display a clear message when a player has no saved, in-progress games to continue.
- **FR-003**: System MUST allow a player to explicitly save their current game progress and return to the stories screen without ending the game. An explicit save MUST record a labelled, timestamped checkpoint marker on that game and confirm the save visibly and briefly to the player (Constitution "Save and session behaviour" #2). The label MUST be generated by the system from the game's current in-fiction location and the time of the save; the player MUST NOT be asked to name a checkpoint, so saving stays a single action with no text entry.
- **FR-003a**: Checkpoint markers MUST NOT act as rewind points — resuming a game MUST always continue from its latest state, never from an earlier marker, and no marker MUST ever discard turns taken after it. Explicit saving persists nothing that autosave (see `008-core-gameplay` FR-017) has not already persisted; it adds the marker and the confirmation.
- **FR-004**: System MUST prompt a player to save their progress when they attempt to log out while a game is currently in progress, and MUST NOT prompt them when no game is in progress or the game has already concluded. The prompt MUST state that the player's progress is already safe, rather than implying progress will be lost if they decline.
- **FR-005**: Accepting the logout save prompt MUST record a checkpoint marker on that game and confirm the save before logging the player out. Declining MUST log the player out without recording a marker and MUST NOT discard, roll back, or otherwise lose any turn already taken — a player's resumable progress is identical whether they accept or decline (Constitution "Save and session behaviour" #3).
- **FR-006**: Resuming a saved game MUST restore play in a state consistent with everything that happened before it was saved.
- **FR-006a**: When recording a checkpoint marker fails, System MUST still complete the logout or return-to-stories the player requested, and MUST tell the player the checkpoint was not recorded while confirming that their progress is safe. A failed checkpoint MUST NOT block, delay, or reverse the player's departure from the game.
- **FR-007**: Each distinct persistence outcome (continue with saved games present, continue with none present, explicit save, resuming a game after a checkpoint was recorded, failed checkpoint recording, resuming a game while another is active, logout-with-save-accepted, logout-with-save-declined, logout with no active game) MUST have a corresponding automated test verifying its expected behavior.

### Key Entities

- **Saved Game**: The persisted state of a player's in-progress Play Session (see `008-core-gameplay`), associated with the player identity that owns it, resumable via the continue-game flow.
- **Checkpoint Marker**: A labelled, timestamped record of a point at which a player explicitly saved a Saved Game. Its label is system-generated from the game's in-fiction location at that moment plus the save time. Belongs to exactly one Saved Game and is descriptive history only — it holds no separate copy of game state and cannot be resumed from.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A player who explicitly saves and returns home, or who saves via the logout prompt, can later resume their game with progress matching exactly what existed at the point of saving.
- **SC-002**: 100% of continue-game lists in testing show only the requesting player's own saved games.
- **SC-003**: 100% of logout attempts while a game is in progress in testing trigger the save prompt; 100% of logout attempts with no active game do not.
- **SC-004**: 100% of tested checkpoint-recording failures still complete the requested logout or return to the stories screen, and surface a message stating the checkpoint was not recorded and that progress is safe.

## Assumptions

- "Games associated to profile" (continue-game listing) refers to play sessions started by the same authenticated player identity (see `002-login-and-access-control`); no sharing or transfer of saved games between identities is in scope.
- Declining the save prompt on logout does not delete or roll back the game and does not lose any turn; the only consequence is that no checkpoint marker is recorded for that logout.
- The save prompt covers the application's own sign-out action. A player who closes the browser, loses their session, or whose token expires is not prompted — nothing is lost in those cases either, since every turn is already persisted as it happens.
- There is no defined limit on the number of in-progress saved games a single player may have across different adventures.
